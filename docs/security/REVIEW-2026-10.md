# Security review — October 2026 (Module 2, Task 8)

Status: **review complete (3 Oct 2026).** Every item on the checklist was reviewed; findings 1–14 are fixed and
unit-tested, and what is still open is listed at the end. None of this has been run end to end against a database: the
e2e suite needs Docker (see `test/task-limits.e2e-spec.ts`, `test/task-issue.e2e-spec.ts`,
`test/campaign-lifecycle.e2e-spec.ts`), and the migrations `20261003120000_encrypt_kyc_document_numbers` and
`20261003130000_finance_team_role` were written by hand.

Severity: High = exploitable by any signed-in user or anonymous caller; Medium = needs a specific role or setup;
Low = information leak or hardening.

## Fixed

### 1. Rate limiting was not enforced anywhere — High
`ThrottlerModule` was configured but `ThrottlerGuard` was never registered, so every `@Throttle` limit (login,
registration, OTP send/verify, password reset, new-device code) did nothing.
**Fix:** `AppThrottlerGuard` (`src/common/guards/app-throttler.guard.ts`) registered as a global guard after
`JwtAuthGuard`. It tracks signed-in callers by account (many Indian mobile users share one carrier IP) and anonymous
callers by `req.ip`. Skipped only when `NODE_ENV=test` (the e2e suite).
**Correction during review:** the first version tracked `req.ips[0]`, the leftmost `X-Forwarded-For` entry, which the
client controls: anyone could dodge every limit by sending a new fake address each time. It now uses `req.ip`, which
Express resolves through the trusted proxy (`TRUST_PROXY`). Regression test in `app-throttler.guard.spec.ts`.
**Note:** the throttle store is in memory, per process. Fine for one cPanel instance; needs a Redis store if the
backend ever runs more than one instance.

### 2. Duplicate records came back as HTTP 500 — Low
Nest gives precedence to the global exception filter registered *last*. The catch-all `GlobalExceptionFilter` was
registered after `PrismaExceptionFilter`, so Prisma's unique-violation (P2002) never reached the Prisma filter and
became a 500. **Fix:** order swapped in `app.module.ts`, with a comment. (Verified with a minimal Nest app: with the
old order the catch-all handled the error; with the new order the Prisma filter does.)

### 3. Constraint names leaked in conflict messages — Low
P2002 messages named the database constraint fields (e.g. `userId_accountNumberHash_ifscCode`).
**Fix:** generic "This record already exists." (`prisma-exception.filter.ts`).

### 4. Any merchant could fund another merchant's campaign — High
`POST /merchants/:merchantId/campaigns/:campaignId/fund` checked that the caller owns `merchantId`, but never that the
campaign belongs to that merchant, so a merchant could activate (and spend the wallet budget of) any approved campaign.
**Fix:** `CampaignService.fundForMerchant` refuses another merchant's campaign as not found. Unit tests in
`campaign.service.spec.ts`; e2e in `campaign-lifecycle.e2e-spec.ts`.

### 5. Support tickets could be linked to anyone's task submission — Medium
The public ticket form (`POST /support/tickets`) accepted any `campaignTaskId` / `submissionId`, so a user could attach a
ticket to someone else's submission (misleading support staff), and an unknown id caused a database error.
**Fix:** the public form no longer accepts links (`forbidNonWhitelisted` returns 422). Links are set only by
`POST /tasks/:taskId/report-issue`, which checks the submission belongs to the caller and to that task.

### 6. Raw SQL, Swagger, static files — confirmed fine
- No `$queryRawUnsafe` / `$executeRawUnsafe` anywhere; every raw query is a tagged template (parameterised).
- Swagger is mounted only when `NODE_ENV !== 'production'` (`main.ts`).
- Static file serving exposes only `uploads/profile`, `campaign`, `cms` and `stories`. KYC documents and submission
  proofs are not publicly served.

### 7. Any account could join a merchant team with a leaked invite link — High
`POST /merchants/accept-invite/:token` was public and took `userId` and `email` from the request body, comparing the
invitation's email with the one *typed in*. Anyone holding a link could attach any account, with the invited role.
**Fix:** the route needs sign-in, takes the account and its real email from the session, and compares emails without
regard to case. The token moved from the path to the body (`AcceptInviteDto`), so request logs no longer record it.
No client called the old route. Tests in `public.controller.spec.ts`, `team.service.spec.ts`.

### 8. Merchant team roles were never enforced — High
`MerchantTeamRoleGuard` existed but no route used it: any team member, even a Viewer, could change bank accounts,
request refunds, recharge the wallet, manage webhooks and the team, and promote themselves to Owner. Suspended members
also kept access, since only `deletedAt` was checked.
**Fix:** the ownership guards resolve the caller's role (`resolveMerchantTeamRole`: the owner is always `OWNER`,
inactive members are refused) and every write route now carries `@TeamRoles(...)` per `MERCHANT_TEAM_PERMISSIONS`:
account, money, bank, team, webhooks and profile/KYC need Owner or Admin; campaigns, tasks, reviews and support also
allow Manager; reading stays open to every active member. The owner role can no longer be granted by invite or update,
nor the owner's role changed. Tests in `merchant-ownership.guard.spec.ts`, `merchant-role.guard.spec.ts`,
`team.service.spec.ts`.
**Note:** team members can not use the merchant portal yet (`GET /merchants/me` finds only the owner's merchant, and
the portal has no accept-invite page), so nobody using the portal today is affected.

### 9. Money actions were open to every admin — Medium
**Fix:** role slugs map to the `AdminRole` names (`super-admin` → `SUPER_ADMIN`), a `finance-team` role exists (seed
and data migration `20261003130000_finance_team_role`), and super admins pass every role check. Withdrawal decisions,
refund decisions, manual top-ups and their review, reward clawback, settlement generation, credit/debit notes and the
TDS register need `FINANCE_TEAM` or `SUPER_ADMIN` (`FINANCE_ROLES`). Super admins give and remove `ADMIN` and
`FINANCE_TEAM` on the Users page (`PUT/DELETE /admin/users/:id/roles/:role`, audited); removing one signs the person
out everywhere. `GET /auth/me` now lists roles. Tests in `finance-routes.spec.ts`, `roles.guard.spec.ts`,
`user-management.service.spec.ts`. This replaces the earlier attempt that was reverted because the slugs never matched.
**Before deploying:** make sure the production super admin account exists and can sign in. Until a super admin gives
someone the finance role, only super admins can approve withdrawals.

### 10. Upload content was not checked — Medium
Uploads trusted the client-declared MIME type. The stored extension was already safe (fixed list), but a program or an
HTML page could be stored as an "image". **Fix:** `contentMatchesMimeType` (`storage/file-signature.util.ts`) checks
the file's opening bytes against its claimed type before the virus scan and before anything is written; a mismatch is
refused with `FILE_TYPE_NOT_ALLOWED`. No new dependency.

### 11. PAN and Aadhaar numbers were stored in plain text — Medium
**Fix:** every user KYC document number, and the PAN copied onto TDS deductions, is encrypted with the same
`FieldCipher` as bank details (`IdentityNumberProtector`), with a keyed hash (`documentNumberHash`) for the shared-PAN
fraud check and admin search (now exact-number only). Masked everywhere (`****234F`), including the person's own KYC
list; revealed only to the admin reviewing that document and in the TDS CSV export used for filing.
`npm run db:encrypt-bank-details` now also encrypts existing KYC numbers and TDS PANs; the deploy script already runs it.
**Not covered:** `Merchant.panNumber` (a business PAN, unique-indexed) is still plain text.

### 12. Two-factor sign-in was never asked for — Medium
**Fix:** a password sign-in to an account with two-factor on is held for a code even on a known device, reusing the
new-device challenge (`NEW_DEVICE_LOGIN` code, which the public OTP endpoints can not reach). The response says why
(`reason: TWO_FACTOR | NEW_DEVICE`) and the portals and app word the code screen to match. The new-device alert email
goes out only for a new device. An account with two-factor on and nowhere to send a code is refused rather than let
through. Google/Apple sign-in is not asked for a code: the code would go to the same mailbox the provider just verified.

### 13. A stolen refresh token could be used forever — Medium
Reusing a rotated refresh token was simply refused, so an attacker who used a stolen token first kept a working chain.
Rotation also dropped the session's device and "remember me", and two sign-ins in the same second could get identical
tokens. **Fix:** presenting a refresh token whose session was rotated or revoked more than 30 seconds ago revokes every
session of the account (inside 30 s it is treated as two tabs refreshing at once and just refused); rotation is atomic,
so only one of two simultaneous refreshes wins; the new session keeps the device and remember-me; each token has a
unique `jti`. Tests in `session.service.spec.ts`, `auth.service.spec.ts`.

### 14. Secrets in logs — Low
Searched every Winston call. Fixed: marketplace redemption codes were logged in full (now the redemption id), and
invite tokens were in logged request URLs (see 7). Confirmed: no passwords, OTP codes, access or refresh tokens, or
account numbers are logged; request logs record method, URL, status, IP and user agent, never bodies. Email addresses
are logged when mail is sent (`MailService`): personal data, but not a secret.

### Also confirmed
- JWT: HS256 pinned on sign and verify, issuer and audience checked, access tokens 15 minutes, refresh tokens stored as
  SHA-256 hashes and rotated on use.
- Merchant child records (campaigns, reviews, tickets, webhooks, invoices, notes, bank accounts, refunds, team members,
  invitations, KYC files, campaign tasks) are all checked against the merchant in the path. User routes with an id
  (bank accounts, withdrawals, tickets, notifications, KYC files, saved campaigns) check the caller.

## Still open

| Item | Notes |
|---|---|
| Merchant webhooks (SSRF) | Webhooks are stored but **nothing sends them**, so there is no SSRF today. Delivery, when built, must block private, loopback, link-local and metadata addresses (after DNS, and on redirects), require https and time out. |
| `Merchant.panNumber` | Business PAN still in plain text; encrypt like KYC numbers (needs a hash column for its unique index). |
| Merchant portal role awareness | The portal does not know a team member's role and would show actions the server now refuses. Matters once team members can use the portal. |
| Admin portal money buttons | Plain admins still see Approve/Pay buttons and get a 403 message. Hide them using `roles` from `/auth/me`. |
| Throttle store | In memory per process; needs Redis storage if the backend ever runs more than one instance. |
| End-to-end run | None of the above has run against MySQL; run `npm run test:e2e` with Docker before release. |
