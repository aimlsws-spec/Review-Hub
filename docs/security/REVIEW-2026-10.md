# Security review — October 2026 (Module 2, Task 8)

Status: **partly done.** Findings 1–6 are fixed and unit-tested. The checklist at the end lists what has not been
reviewed yet. None of this has been run end to end against a database: the e2e suite needs Docker (see
`test/task-limits.e2e-spec.ts`, `test/task-issue.e2e-spec.ts`, `test/campaign-lifecycle.e2e-spec.ts`).

Severity: High = exploitable by any signed-in user or anonymous caller; Medium = needs a specific role or setup;
Low = information leak or hardening.

## Fixed

### 1. Rate limiting was not enforced anywhere — High
`ThrottlerModule` was configured but `ThrottlerGuard` was never registered, so every `@Throttle` limit (login,
registration, OTP send/verify, password reset, new-device code) did nothing.
**Fix:** `AppThrottlerGuard` (`src/common/guards/app-throttler.guard.ts`) registered as a global guard after
`JwtAuthGuard`. It tracks signed-in callers by account (many Indian mobile users share one carrier IP) and anonymous
callers by `req.ip`. Skipped only when `NODE_ENV=test` (the e2e suite).
**Correction during review:** the first version tracked `req.ips[0]`, the leftmost `X-Forwarded-For` entry, which the
client controls: anyone could dodge every limit by sending a new fake address each time. It now uses `req.ip`, which
Express resolves through the trusted proxy (`TRUST_PROXY`). Regression test in `app-throttler.guard.spec.ts`.
**Note:** the throttle store is in memory, per process. Fine for one cPanel instance; needs a Redis store if the
backend ever runs more than one instance.

### 2. Duplicate records came back as HTTP 500 — Low
Nest gives precedence to the global exception filter registered *last*. The catch-all `GlobalExceptionFilter` was
registered after `PrismaExceptionFilter`, so Prisma's unique-violation (P2002) never reached the Prisma filter and
became a 500. **Fix:** order swapped in `app.module.ts`, with a comment. (Verified with a minimal Nest app: with the
old order the catch-all handled the error; with the new order the Prisma filter does.)

### 3. Constraint names leaked in conflict messages — Low
P2002 messages named the database constraint fields (e.g. `userId_accountNumberHash_ifscCode`).
**Fix:** generic "This record already exists." (`prisma-exception.filter.ts`).

### 4. Any merchant could fund another merchant's campaign — High
`POST /merchants/:merchantId/campaigns/:campaignId/fund` checked that the caller owns `merchantId`, but never that the
campaign belongs to that merchant, so a merchant could activate (and spend the wallet budget of) any approved campaign.
**Fix:** `CampaignService.fundForMerchant` refuses another merchant's campaign as not found. Unit tests in
`campaign.service.spec.ts`; e2e in `campaign-lifecycle.e2e-spec.ts`.

### 5. Support tickets could be linked to anyone's task submission — Medium
The public ticket form (`POST /support/tickets`) accepted any `campaignTaskId` / `submissionId`, so a user could attach a
ticket to someone else's submission (misleading support staff), and an unknown id caused a database error.
**Fix:** the public form no longer accepts links (`forbidNonWhitelisted` returns 422). Links are set only by
`POST /tasks/:taskId/report-issue`, which checks the submission belongs to the caller and to that task.

### 6. Raw SQL, Swagger, static files — confirmed fine
- No `$queryRawUnsafe` / `$executeRawUnsafe` anywhere; every raw query is a tagged template (parameterised).
- Swagger is mounted only when `NODE_ENV !== 'production'` (`main.ts`).
- Static file serving exposes only `uploads/profile`, `campaign`, `cms` and `stories`. KYC documents and submission
  proofs are not publicly served.

## Reverted

### Finance-only roles on money actions — not applied
An earlier attempt changed withdrawal approval/payment, refund decisions, manual top-ups and reward clawback to
`@Roles(FINANCE_TEAM, SUPER_ADMIN)`. Those roles **do not exist** in practice: the token carries the role *slugs*
uppercased (`ADMIN`, `SUPER-ADMIN`, ...), no finance role is seeded, and `SUPER-ADMIN` (hyphen) never equals
`SUPER_ADMIN`. The change locked every admin, including the super admin, out of all money actions, so it was reverted
to `SystemRole.Admin`.
**Still recommended**, as a separate piece of work that needs a product decision: seed a finance role, decide whether
plain admins keep money powers, give the admin portal a way to assign roles, and normalise slugs to the `AdminRole`
enum (`super-admin` → `SUPER_ADMIN`) in `UserRepository.getRoleNames`.
