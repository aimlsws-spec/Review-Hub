## Phase 3 — Trust

### Task 7: Dispute workflow

**What**: Let a user formally dispute a rejected task submission or reward, distinct from the 
existing general support-ticket system. Gives admins a structured queue to review and reverse or 
uphold rejections.

**Why**: Right now a rejected user has no path back except a generic support ticket with no link to 
the actual submission record — no reason captured, no admin queue, no resolution notification.

**Scope** (confirmed with the user earlier): user disputes a *rejected submission/reward* only. Not 
merchant-side disputes, not fraud-flag disputes — those are separate existing systems.

**Backend — investigate first**: 
- Read `apps/backend/src/modules/task/services/submission.service.ts` (the `approve`/`reject`/
  `finalizeApproval`/`finalizeRejection` methods) — a dispute resolution will call the same 
  `finalizeApproval`/`decide` machinery to reverse a rejection.
- Read `apps/backend/src/modules/task/events/` (`SubmissionApprovedEvent`, `SubmissionRejectedEvent`) 
  for the event-emission pattern a `DisputeResolvedEvent` should follow.
- Read `apps/backend/src/modules/admin/controllers/kyc-management.controller.ts` and its service for 
  the shape of an "admin review queue" (list pending, approve, reject with reason) — a dispute queue 
  is structurally almost identical.
- Read `apps/backend/src/shared/audit/audit-log.service.ts` usage patterns — every admin decision on 
  a dispute must be audit-logged, exactly like KYC/fraud decisions are.

**Suggested schema** (design it properly, this is a starting point not a spec): a `Dispute` model — 
`id` (UUID), `submissionId` (FK to `TaskSubmission`), `userId`, `reason` (text, required), 
`status` (enum: `OPEN`, `UNDER_REVIEW`, `UPHELD`, `REVERSED`), `adminNotes` (text, nullable), 
`resolvedBy` (nullable FK to admin user), `resolvedAt` (nullable), standard `createdAt`/`updatedAt`/
`deletedAt`. One dispute per submission (unique constraint on `submissionId`) — a user can't dispute 
the same rejection twice while one is already open.

**Backend endpoints**:
- `POST /submissions/:id/dispute` (user, authenticated) — only allowed if the submission's status is 
  `REJECTED` and no dispute already exists for it.
- `GET /admin/disputes` (admin) — paginated list, filterable by status.
- `POST /admin/disputes/:id/resolve` (admin) — body: `{ decision: 'UPHELD' | 'REVERSED', notes: 
  string }`. `REVERSED` should call through to the same reward-crediting path a normal approval uses 
  (reuse `SubmissionService`'s approval logic — don't duplicate the reward/participant-progress 
  math).

**Notification on resolution**: find the existing notification-on-decision pattern (search for how 
`SubmissionApprovedEvent`/`SubmissionRejectedEvent` currently trigger a push/in-app notification — 
likely a listener in the notification module) and add the same for dispute resolution.

**Mobile**:
- On a rejected submission (find `my_submissions_screen.dart` and/or the submission detail view), 
  add a "Dispute this rejection" action that opens a small form (reason, optional extra evidence) and 
  posts to the new endpoint.
- Show dispute status (open/under review/resolved) wherever the submission itself is shown.

**Admin portal**: new page mirroring `FraudFlagsPage.tsx` or the KYC review page — a table of open 
disputes, a detail view with the original submission/rejection reason, and Uphold/Reverse actions 
with a notes field.

### Task 11: Backend mobile ID-token verification endpoints

**What**: The backend currently only supports Google/Apple sign-in via a browser-redirect OAuth flow 
(used by the web portals). Mobile needs endpoints that accept a native SDK's ID token directly and

**Investigate first**:
- `apps/backend/src/modules/auth/strategies/google.strategy.ts` and `apple.strategy.ts` — the 
  existing web-redirect strategies. Do NOT try to reuse Passport's redirect-based strategy for this — 
  mobile needs direct token verification, a different flow.
- `apps/backend/src/modules/auth/controllers/auth.controller.ts` — see the existing `/auth/google`, 
  `/auth/google/callback`, `/auth/apple` endpoints and how a successful OAuth login currently issues 
  JWT/refresh tokens (find the shared method that builds the token pair — reuse it exactly, don't 
  duplicate token-issuance logic).
- `apps/backend/src/modules/auth/services/auth.service.ts` for the login/registration logic tied to 
  an external-provider profile (look for how `provider: 'google'` is currently handled in 
  `googleAuthCallback`).

**New endpoints**:
- `POST /auth/google/mobile` — body `{ idToken: string }`. Verify the token against Google's public 
  keys (use `google-auth-library`'s `OAuth2Client.verifyIdToken`, a well-known package for this — 
  resolve its current version via `npm view google-auth-library version`, don't guess). Extract the 
  verified email/name/subject, then run through the same find-or-create-user + issue-tokens path the 
  web callback uses.
- `POST /auth/apple/mobile` — body `{ identityToken: string }`. Apple's tokens are verified against 
  Apple's JWKS endpoint — check if a suitable library already exists as a dependency (search 
  `package.json` for anything Apple/JWT-related tied to the existing `apple.strategy.ts`) before 
  adding a new one.
- New env vars in `apps/backend/.env.example` (placeholders, empty by default): `GOOGLE_MOBILE_CLIENT_ID` 
  and whatever Apple's mobile verification needs (Team ID / Service ID / Key ID — check what 
  `apple.strategy.ts` already expects via its existing `APPLE_*` env vars and extend consistently 
  rather than inventing new names).
- Config validation: if these env vars are the same shape as `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` 
  (optional, feature disabled gracefully when absent), follow that exact pattern — check 
  `apps/backend/src/config/envs/payment.config.ts` for how an optional integration's config is
